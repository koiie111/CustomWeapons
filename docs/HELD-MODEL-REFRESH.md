# Обновление модели в руках — 1.0.4-rc.4

10.11.2026 один реальный клиент на публичном #10 подтвердил смену нескольких моделей через меню и сохранение выбранной модели после подбора своего AK, переключения на пистолет и обратно. Исправление выполняется новым экземпляром. Короткое переключение того же экземпляра в rc.1 не обновляло вид в руках; этот вариант отклонён.

## Поведение

После фактического изменения модели в ApplyInventory, выбора в меню, pickup/equip ставится одна объединяемая проверка на session. Проверяются полные handles контроллера и pawn, session, поколение карты, активный экземпляр и его владелец. Кэш до 64 записей связывает handle/pawn/модель/definition: повторный equip и подбор своего уже обновлённого экземпляра не требуют новой выдачи. Stock reversion неактивного оружия помечается до следующего equip.

Перед заменой собирается снимок. Неизвестные/дублирующиеся атрибуты, неоднозначный целевой слот, недоступный item service или неотсоединённый handle прекращают операцию до удаления оружия. Штатный `DropActivePlayerWeapon` должен убрать именно старый handle из MyWeapons; затем запрашивается удаление entity. Выдача ждёт невалидности полного старого serial. Доступны восемь попыток; исчерпание выдачи записывается в журнал для административного восстановления. Слот, занятый новой сторонней выдачей, не вытесняется.

Новый экземпляр получает сохранённые clip/reserve и только относящиеся к нему общие ammo pools, режимы burst/silencer, recoil/accuracy, более строгое из старого и нового ограничение атаки, paint/seed/wear/StatTrak, имя, account/original owner и оба вектора атрибутов. Новый item ID не заменяется старым. Модель и mesh восстанавливаются после выдачи. На следующем кадре оформление применяется ещё один раз после отложенных give hooks; ammo повторно не записывается, чтобы не вернуть потраченные патроны.

Гранаты и C4 не перевыдаются и не используются как целевые слоты. Второй ствол для замены не нужен. Перевыдача прерывает текущее действие оружия как обычный deploy; это не сохранение незавершённой перезарядки/прицела. Native subclass восстанавливается, если сторонний give hook выдал другой definition. Выбор при смерти сохраняется и применяется к будущему оружию как раньше.

Смерть, spawn, disconnect, замена session, карта и round start/end отменяют отложенную работу. Перед каждой стадией проверяются pawn/владелец/полный handle. При unload доступный незавершённый удалённый экземпляр восстанавливается с исходной моделью; на другой pawn или карту он не выдаётся. Поддерживается возврат к позднее выбранному rifle/pistol/knife через стандартную команду слота; прочие быстрые переключения и сторонние цепочки ещё требуют игровой проверки.

## CSS и атрибуты

CSS 375/установленный 378 не перечисляет `NetworkedVector<CEconItemAttribute>`: его indexer принимает только CHandle. Для element zero нативный accessor возвращает адрес буфера; размер CEconItemAttribute берётся из текущей схемы движка, фиксированный stride/offset не используется. Проверяются count ≤ 256, ненулевой buffer и размер класса 1…4096. Доступ нужен только при замене.

Источники API: [NetworkedVector.cs](https://github.com/roflmuffin/CounterStrikeSharp/blob/v1.0.375/managed/CounterStrikeSharp.API/Core/Model/NetworkedVector.cs), [native accessor](https://github.com/roflmuffin/CounterStrikeSharp/blob/v1.0.375/src/scripting/natives/natives_memory.cpp), [item services](https://github.com/roflmuffin/CounterStrikeSharp/blob/v1.0.375/managed/CounterStrikeSharp.API/Core/Model/CCSPlayer_ItemServices.cs).

285 имён атрибутов извлечены из установленного официального `pak01`/`scripts/items/items_game.txt` с проверкой CRC VPK; SHA256 исходного items_game — `1edea31ef2af0a46d1b38b4e4a6337de534bb61629f4b527137617ef03879fed`. Таблица встроена в DLL. Native setter имеет отдельный ключ `CW_SetOrAddAttributeValueByName` в `gamedata/customweapons.json`; сигнатуры соответствуют установленному setter WeaponPaints. Gamedata входит в пакет, CounterStrikeSharp.API не распространяется с ним.

## Оптимизация и проверки

Существующие grenade OnTick/OnEntitySpawned по-прежнему отсутствуют в конфигурации без гранат. Два повторяющихся таймера и ранний `_applied` guard сохранены. В safety callback только фактическая запись модели может поставить событийную проверку. Нового тик-слушателя или периодического обзора игроков/оружия нет. В рабочей очереди общий бюджет ограничивает retire/grant/appearance-settlement четырьмя единицами за Server.TickCount; ожидание бюджета не расходует попытки выдачи. После завершения очереди работы нет.

129 managed проверок используют реальные production callbacks с подменой границы CSS. Включены повторные события выдачи, неизвестные атрибуты до удаления, полные serials, ammo/mesh/cooldowns, передача оформления, C4, отложенная перепокраска без возврата патронов и серии по 100 equip для 0/1/8/32 игроков. Они не доказывают нативный порядок событий или рендер.

Сравнение perf.2 (`879fc5f`) и rc.4: [raw и frozen inputs](performance/held-replacement-20261110/), .NET 10, TieredCompilation=0, одинаковый harness, 32 игрока, 0/1/8/32 гранатодержателя, 2 000 warmup, 3 × 10 000 вызовов tick/safety. Во всех 24 парах совпали allocations, player scans, definition reads и model writes. Медианы ns/call:

| Держателей | tick perf.2 / rc.4 | safety perf.2 / rc.4 |
|---|---|---|
| 0 | 24.5 / 22.1 | 3112.8 / 3075.6 |
| 1 | 80.3 / 68.2 | 3097.0 / 3111.0 |
| 8 | 446.3 / 461.6 | 3221.1 / 3309.1 |
| 32 | 1907.2 / 1832.5 | 3689.6 / 3751.8 |

Это изолированные managed callback окна, не весь tick/CPU и не стоимость native перевыдачи. Cold population/очередь не исполняются внутри окон; новое событийное действие проверяется отдельно, его скорость не объявлена равной perf.2. Время зависит от стенда, малые различия не трактуются как ускорение. Замеры rc.1 сохранены отдельно в `held-refresh-20261110`; исходные hashes/цифры perf.2 из `7835020` сохранены в историческом source archive и не пересчитаны.

## Игровая приёмка и границы

- На #10 exact DLL `69b19fff54b6beb4343a94336f7338dd17bd974eee519f76e9994d2142397478`, Core `ea791ada89e3778f74c45c0e482a5c581d9650c30410ef439366f0647860f471` прошли 25 последовательных нативных проверок снимка: один приобретённый новый AK, старый serial отсутствует, ammo, mesh/cooldown, три обычных и два dynamic attributes сохранены, включая точные биты float.
- Это вызовы production WeaponState на контролируемом боте, не весь production pipeline человеческой session. Ранние невалидные fixtures сохранены: бот уже держал SSG (возвращался unowned AK), затем обвязка ошибочно удаляла C4 после неудачного drop. Исправлена только обвязка: очищается rifle, проверяется detach и первоначальное приобретение. Эти провальные прогоны не зачтены.
- Один клиент подтвердил смену нескольких моделей в руках и pickup своего AK с переключением на пистолет/обратно. Точные имена/число всех испробованных моделей отдельно не трассировались. После последнего pickup клиент вышел до server-side снимка: точное равенство его финального ammo не заявляется. Сохранение состояния проверено отдельно unit/native fixture.
- Два клиента, !wp/переход раунда с реальным клиентом, ножи/все aliases, reconnect/death/map именно rc.4 и полный tick/GC под нагрузкой не приняты. Результаты perf.2 не подменяют эти проверки новой сборки.

После выхода владельца #10 возвращён к исходной 1.0.2: совпали все 243 исходных DLL, CW config и gamecfg; preferences сохранены, все 60 исходных модулей загружены, entry открыт. Помощник архивирован вне autoload, добавленная gamedata удалена. На #7 сначала произошло пересечение с тестом WeaponPaints; тот агент согласованно восстановил только изменения CustomWeapons. #7 остаётся за его проверкой. Массовой выкладки не было.

[Sanitized native fixture, контрольные суммы и восстановление](acceptance/held-model-20261110/) проверяются `python docs/acceptance/held-model-20261110/verify.py`. Проверенная сборка сделана из рабочего дерева с parent `879fc5f`; архив входов фиксирует точный production source.
