## Покрытие O4

| Требование | Реализация и проверка |
|---|---|
| Предвычисленный lookup, отсутствие повторной нормализации в OnTick | `IsProjectileWeapon` использует HashSet; OnTick не читает item definition. Уже оформленные handles теперь пропускаются до Resolve и в ApplyInventory. Forced выбор/сброс сохраняют прежнюю обработку. |
| Sessions и tracked holders | Controller handle с serial, набор слотов держателей, события spawn/pickup/equip и сверка инвентаря 0,5 с. Disconnect/map/unload очищают набор; death/drop замечаются сверкой. |
| Capture перед удалением оружия | При включённых гранатах сохранены OnTick и OnEntitySpawned, полный capture на spawn и NextFrame projectile → Thrower/OriginalThrower → модель. При gun-only конфиге оба grenade listeners отсутствуют. |
| Inventory safety и DB | Полный набор handles с serial вместо lossy hash; изменённый инвентарь применяется сразу на сверке, неизменный — по safety deadline. События и завершение актуального DB refresh продолжают применять модели. Права, expiry/server scope и сохранение модели переданного экземпляра не менялись. |

## Найдено и исправлено

1. **P2: DB result переживал смену карты.** `RequestRefresh` проверял identity
   сессии, но не поколение карты. Завершение запроса с предыдущей карты могло
   опубликовать старый каталог/доступы и вызвать ApplyInventory уже на новой.
   Теперь snapshot публикуется только в текущем поколении и при готовой карте;
   stale completion освобождает single-flight и запускает актуальное чтение,
   если новая карта уже готова. Регрессия `map-only` падает на прежнем коде с
   `Old-map read cannot publish catalog` и проходит после исправления.
2. **Неполные проверки плана.** Core-тесты не вызывали реальные registration,
   holder/timer/capture/DB callbacks. Добавлен [Runtime harness](../tests/Runtime/README.md),
   который компилирует production source с заменами границы CSS; 59 проверок
   проходят. Он также измеряет неизменённые baseline и candidate callbacks
   одинаковым способом. Это дополнение к реальной сборке против CSS API.
3. **Повторные definition reads.** При обычном ApplyInventory проверка `_applied`
   стояла после Resolve. Перенесена перед чтением definition/нормализацией;
   переданные оформленные экземпляры по-прежнему сохраняют свою модель.
4. **Raw evidence было доступно только локально.** Все 20 оригинальных
   Speedscope exports теперь включены в архив с SHA256; независимый verifier
   пересчитывает каждый window и агрегированные mean/p50/p95/p99/max.

Новый номер perf.2 отличает изменённый production-код от измеренной perf.1.
Версии зависимостей, конфиг, SQL/права, частота ввода и гранатных callbacks
не менялись. Обращения к native entities остаются в игровом потоке.

SDK 10.0.400, net10.0, CounterStrikeSharp.API 1.0.375; locked dependencies.
Baseline c52b926: Release 0 предупреждений/ошибок, 54 unit passed / 1 MySQL
integration skipped локально. Исходный main/PR: 57 passed / 1 skipped.
Исправленный candidate: Release 0 предупреждений/ошибок, 57 passed / 1 skipped,
59 runtime checks, raw/synthetic verifiers и package validation пройдены.
CI запускает тот же runtime suite и MySQL integration на disposable MySQL 8.4.

Synthetic: 32 connected, 0/1/8/32 holders, 2000 warmup и 3 × 10000 calls каждого
пути, tiered JIT выключен. Production baseline и candidate source/Core подключены
по отдельности. Все 24 пары окон сохраняют 32 нанесённые модели и одинаковые
input/iteration counts. На candidate OnTick нет полного GetPlayers/definition
reads; на safety полный player/inventory scan остаётся. Снижение вызовов
ApplyInventory проверяется счётчиком чтений на **неоформленном** оружии;
изменение инвентаря и принудительный safety deadline восстанавливают попытку.

Raw и условия воспроизведения: [review-20261110](performance/review-20261110/),
[README harness](../tests/Runtime/README.md). Аллокации включают управляемые
замены CHandle; doubles GetPlayers не моделируют native allocations. Нет
основания переводить эти величины в проценты CPU сервера. Safety по времени
не ускоряется последовательно; уменьшение его allocations не скрывает scan
и стоимость сортировки/сравнения handles.

## Сохранённый CSSProfiler эксперимент и границы вывода

[Отчёт perf.1](PERFORMANCE-CSSPROFILER-20261110.md) описывает пустой #17:
baseline/main/perf.1, по три 30-секундных окна idle/entities, ещё два окна
enabled-grenade branch. Пересчёт raw подтвердил 10.705 → 6.124 → 2.069 мс
covered CW callbacks на окно entity workload. Это −66.2% от прежнего main
или −80.7% от pre-O4 только в указанном synthetic entity workload;
абсолютная разница main → perf.1 — около 4.055 мс за 30 с.

Профили не охватывают AddTimer/NextFrame, allocations/GC и full tick. Нет
повторного baseline, полноценной steal/throttle/neighbor telemetry или
активных клиентов; baseline отличался отсутствием entry-lock. Эти ограничения
сохранены. Enabled-grenade branch проверяла регистрацию и invalid handle,
а не реальные броски. Данные не являются серверным профилем perf.2 и не
закрывают активный O4 target −25% либо задержку 150 мс.

## Выпуск, откат и игровая приёмка

Release package и manifest подготовлены вне web root; SHA256 конкретных DLL
и dependencies — `performance/review-20261110/release-manifest.json`.
Package script не включает CSS API, runtime data или секреты. Сохранить свой
config и data/selections.json, использовать совместимые существующие
dependencies. Перед отдельно разрешённым холодным restart сохранить обе
прежние DLL вне autoload; для отката вернуть обе DLL и исходные зависимости,
config/preferences, если они менялись при отдельном тесте. Текущий diff их
формат не меняет. Безопасный hot reload не обещается: прежние проблемы с
native delegates требуют холодного старта тестового instance.

В этом ревью серверные действия не выполнялись. Владелец предложил провести
игровую приёмку позже на пустом сервере. Следующий шаг: выбрать instance и
проверить **точную perf.2** с клиентом, затем двумя клиентами: HE/flash/smoke/
molotov/incendiary/decoy/snowball, две быстрые flash, switch/throw/pickup,
передачу экземпляра, death/respawn, выдачу другим плагином, private expiry/
DB outage на тестовых данных, reconnect/map lifecycle и меню/вид модели.
Известный вопрос немедленного first-person refresh после выбора сохраняется;
этот perf-патч его не решает и не заявляет новой регрессией.

После функциональной матрицы нужен отдельный сопоставимый активный профиль
OnTick + spawn + safety/NextFrame + full tick/GC. Решение о массовом выпуске
остаётся `awaiting_live`; кодовую реализацию O4 можно отметить завершённой.
